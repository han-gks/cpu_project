# [ADR-009] Trap 처리 및 CSR 갱신 타이밍 비교

**작성일자:** 2026-10-29  
**작성자 / 리뷰어:** 정현재 / 한대규  
**상태:** 요청됨(Requested)  
**영향 범위:** CSR Regfile, Pipeline Registers, Interrupt Controller, Trap Controller, PC Select Logic

## 1. 배경 및 문제 정의 (Context & Problem Statement)

현재 5-Stage Pipeline(IF → ID → EX → MEM → WB) 설계에서 **CSR 갱신 시점과 Trap 발생 시 PC 변경 시점**에 대한 두 가지 의견이 있다.

- **팀원 의견:** CSR 레지스터 변경을 WB 단계에서 일괄 처리하고, 외부 인터럽트 요청도 IF/ID 경로를 통해 전달하는 방식
- **추가 검토 의견:** 일반 CSR 명령어는 WB에서 처리하되, 하드웨어에 의해 변경되는 CSR는 명령어의 WB 타이밍과 분리하는 방식

두 방식 모두 Trap 요청을 인지하면 후속 명령어 Fetch를 Stall한다는 공통 규칙을 적용한다.

## 2. 설계 요구사항 및 제약조건 (Requirements & Constraints)

- 일반 CSR 명령어의 WB Write 구조 유지 고려
- 인터럽트 발생 시 Pending 상태 보존
- Trap 진입 시 `mepc`, `mcause`, `mstatus` 등 갱신
- 이전 명령어의 정상 완료 및 Precise Trap 보장
- Fetch Stall과 PC Redirect 타이밍 정합성 확보

## 3. 고려된 대안 비교 (Considered Alternatives)

| 비교 항목 | 대안 A: 팀원 의견 | 대안 B: 추가 검토 의견 |
|---|---|---|
| CSR 명령어 | WB 갱신 | WB 갱신 |
| CSR 하드웨어 갱신 | WB에서 일괄 처리 | 하드웨어 이벤트에 따른 별도 갱신 |
| `mip` Pending | IRQ 상태를 보존한 뒤 WB 반영 | IRQ 하드웨어 상태를 WB와 독립적으로 반영 |
| `mepc`, `mcause`, `mstatus` | WB에서 갱신 | 실제 Trap 진입 시 갱신 |
| IRQ 전달 | IF → ID 경로 | IF → ID 경로 유지 가능 |
| PC 변경 | WB 중심 | EX 조기 변경 검토 |
| 장점 | 갱신 시점 통일, 제어 일관성 | IRQ 상태 반영 및 Handler 진입 타이밍 유연성 |
| 고려 사항 | IRQ 보존 및 WB까지의 지연 | CSR Write 충돌 및 Hazard 제어 |

### Option 1: WB 일괄 처리

CSR 갱신을 WB 단계로 통일하여 제어 구조의 일관성을 확보한다.

다만 인터럽트는 명령어 실행과 독립적으로 발생하므로, WB 처리 전까지 IRQ Pending 상태를 보존하고 CPU가 이를 인식할 수 있도록 해야 한다.

### Option 2: 하드웨어 CSR 갱신 경로 분리

일반 CSR 명령어는 WB에서 처리하되, 다음과 같이 구분한다.

```text
CSR 명령어 ──→ WB ─────────→ CSR Bank

외부 IRQ ──→ HW Pending ──→ mip

Trap 진입 ──→ Trap Control ──→
                mepc / mcause / mstatus
```

`mip`는 일반 CSR 명령어의 WB 실행 여부와 독립적으로 Pending 상태를 반영한다.

단, `mepc`, `mcause`, `mstatus`는 IRQ를 감지할 때마다 변경하는 것이 아니라 **실제 Trap 진입이 결정된 시점에 갱신**한다.

PC 역시 EX에서 조기에 변경할 수 있는지 검토하되, 이전 명령어의 실행 완료가 보장되어야 한다.

## 4. 최종 결정 및 근거 (Decision & Rationale)

**선택된 안: 미확정 — 두 방식 비교 검토 요청**

현재 WB 일괄 처리 방식은 CSR 갱신 시점을 통일하여 설계와 검증을 관리하기 쉽다는 장점이 있다.

반면 하드웨어 갱신 경로를 분리하면 명령어와 무관하게 발생하는 인터럽트의 Pending 상태를 직접 반영할 수 있고, Trap 진입 시 PC와 CSR의 변경 시점도 유연하게 설계할 수 있다.

특히 **외부 IRQ 신호를 IF/ID로 전달하는 구조와 하드웨어 CSR 갱신을 분리하는 구조는 동시에 적용 가능하다.**

따라서 두 의견을 반드시 상호 배타적으로 볼 필요는 없으며, CSR 갱신 시점과 PC 변경 시점을 구분하여 검토하고자 한다.

## 5. 예상 부작용 및 후속 조치 (Consequences & Action Items)

**주의할 코너 케이스**

- WB에 CSR 명령어가 없는 동안 IRQ 발생
- CSR Write와 Trap Entry 동시 발생
- IF/ID Stall 중 IRQ 정보 전달
- EX PC 변경 시 이전 Store/CSR Write 미완료
- Trap 진입 후 Pending 상태 유지 및 재진입

**검증 계획 및 후속 조치**

- [ ] Trap Entry 시 CSR Write 충돌 처리 검토
