# [ADR-011] 트랩 처리 타이밍 통합 비교 및 다중 해저드·트랩 우선순위 중재

- **작성일자:** 2026-11-02
- **작성자 / 리뷰어:** 한대규/장병옥, 정현재
- **상태:** 승인됨 (Accepted)
- **영향 범위:** 트랩 제어기 및 해저드 제어 유닛의 전역 Stall/Flush/PC 선택 우선순위

---

### 1. 배경 및 문제 정의

앞서 비동기 인터럽트(ADR-009)와 동기 예외(ADR-010)의 처리 방식을 각각 정의했다. 여기서 두 가지 핵심 아키텍처 질문을 명확히 매듭지어야 한다.

1. **"비동기 인터럽트(ADR-009)와 동기 예외(ADR-010)의 트랩 처리 타이밍은 동일한가?"** — 왜 두 트랩은 파이프라인 제어 방식(Drain vs 순차 Flush 후 WB Commit)과 `mepc` 저장 대상이 달라야 하는가?
2. **다중 이벤트 동시 발생 시 우선순위:** 한 사이클 안에서 동기 예외, 비동기 인터럽트, 버스 대기(Wait-state Stall), EX 분기(Branch Taken), Load-use 정지, CSR 직렬화 정지가 동시에 요청될 때 어떤 순서로 중재해야 파이프라인 데드락(Deadlock)이나 명령어 유실이 발생하지 않는가?

### 2. 요구사항 및 제약조건

- 파이프라인 내부에 동기 예외 명령어가 존재할 때 비동기 인터럽트가 동시에 들어오면, 잘못된 명령어가 실행 완료되는 것을 막기 위해 동기 예외가 먼저 처리되거나 예외 명령어 직전에 정확히 멈춰야 한다.
- 주변장치 버스(APB 등) 접근으로 인해 다중 사이클 대기(`BusStall`)가 걸린 동안에는 메모리 단계의 명령어와 데이터가 유실되지 않도록 파이프라인 레지스터가 보존되어야 한다.
- 모든 제어 신호(Stall 4종, Flush 4종, PC Stall 1종)는 단일 우선순위 결정 트리를 통해 상호 배타적이고 결정론적(Deterministic)으로 생성되어야 한다.

### 3. 대안 비교 및 정량적 타이밍 분석

#### 3.1 동기 예외(ADR-010) vs 비동기 인터럽트(ADR-009) 타이밍 정량 비교

**"두 트랩의 처리 타이밍은 동일한가?" → 동일하지 않다.** 둘 다 최종적으로 **파이프라인에 선행 미완료 명령어가 하나도 남아 있지 않은 시점에 CSR과 PC를 원자적으로 갱신**한다는 원칙은 같지만, 트랩의 발생 원인(명령어 내부 vs 외부)이 다르기 때문에 파이프라인을 비우는 방향과 소비 사이클이 정반대로 동작한다.

| 비교 항목 | 동기 예외 및 `MRET` (ADR-010) | 비동기 인터럽트 (ADR-009) | 왜 다르게 설계해야 하는가? (근거) |
| :--- | :--- | :--- | :--- |
| **발생 원인 및 귀속 대상** | 특정 명령어 내부 (해독 단계 ID에서 검출) | 외부 하드웨어 신호 (특정 명령어에 귀속되지 않음) | 예외는 해당 명령어를 실행하면 안 되지만, 인터럽트는 진행 중인 모든 명령어를 끝내도 무방함 |
| **파이프라인 비우기 방식** | **후속(젊은) 명령어 순차 Flush** + 선행 명령어만 완료 | **전체 파이프라인 배출(Drain)** (IF~WB의 모든 유효 명령어 완료) | 예외 명령어 뒤에 들어온 명령어는 실행되면 안 되므로 즉시 버블로 지워야 함 |
| **감지 후 진입까지 소비 사이클** | **고정 3사이클 전파** + 1사이클 분기 (**총 4사이클 고정**) | **가변 0~4사이클 드레인** + 1사이클 분기 (**파이프라인 잔량에 따라 1~5사이클**) | 파이프라인이 비어 있을 때 IRQ가 오면 0사이클 드레인으로 즉시(1사이클) 진입 가능 |
| **폐기(취소)되는 명령어 수** | 예외 명령어 자신 + 후속 명령어 **1~2개 폐기** | **0개 폐기** (인출된 유효 명령어 전수 완료) | 인터럽트에서 불필요한 명령어 폐기·재실행 방지로 효율 유지 |
| **`mepc` 기록 값** | **`MEM_WB_PC`** (WB에 도달한 예외 명령어 자신의 주소) | **`oPc`** (신규 인출이 정지된 다음 인출 예정 주소) | 예외는 원인 명령어 주소로, 인터럽트는 중단된 다음 명령어 주소로 복귀해야 함 |
| **CSR·PC 최종 갱신 시점** | 예외 명령어가 **MEM/WB에 도달한 사이클** (`MEM_WB_Exc == 1`) | 4개 단계가 **모두 비워진 사이클** (`Valid == 4'b0000`) | 두 경우 모두 **선행 미완료 명령어가 0개인 시점**에 1사이클 원자적 갱신 수행 |

#### 3.2 동기 예외와 비동기 인터럽트 동시 발생 시 우선순위 대안 비교

| 비교 항목 | 대안 A: 비동기 인터럽트 우선 (Drain 먼저 수행) | **대안 B: 동기 예외 최우선 처리 (선택)** |
| :--- | :--- | :--- |
| **동작 방식** | 파이프라인에 예외 명령어가 있어도 인터럽트 Drain을 먼저 수행 | 파이프라인(`ID/EX`, `EX/MEM`, `MEM/WB`)에 예외가 있으면 인터럽트보다 예외 Flush·커밋을 우선 수행 |
| **발생 문제 / 장점** | Drain은 파이프라인의 모든 명령어가 완료(`Valid=0`)될 때까지 기다리는데, 예외 명령어도 `Valid=1`이므로 결국 예외 명령어가 WB에 도달해 충돌 발생 | 예외 명령어가 WB에서 먼저 트랩 진입하면서 **`mstatus.MIE`를 `0`으로 자동 마스킹**하므로, 외부 인터럽트는 Pending(`mip`) 상태로 보존되었다가 예외 처리 후 안전하게 수락됨 |

#### 3.3 전체 파이프라인 해저드·트랩 제어의 6단계 우선순위 표

한 사이클에 여러 제어 요청이 겹칠 때 아래 **1순위 → 6순위** 순서로 중재한다.

| 우선순위 | 제어 조건 | 구동 동작 (`Stall` / `Flush` / `PC`) | 소비 사이클 | 상위 우선순위 부여 근거 |
| :---: | :--- | :--- | :---: | :--- |
| **1순위** | **트랩 분기 확정 (`TrapBranch`)**<br>*(WB 예외 커밋 또는 IRQ 드레인 완료)* | `PC <= mtvec/mepc`, `IF/ID Flush` + `TrapFlush[2:0]` 적용 | 전환 1사이클 | 트랩 진입이 최종 확정된 순간이므로 모든 정지 조건을 무시하고 즉시 핸들러로 점프해야 함 |
| **2순위** | **버스 대기 (`BusStall`)**<br>*(주변장치 APB 다중 사이클 접근 중)* | `PC` 및 **4개 단계 전체 Stall** (`IF/ID` ~ `MEM/WB` 모두 보류) | APB 접근 시 **2사이클 정지** | MEM 단계의 버스 트랜잭션이 끝나기 전에 파이프라인이 움직이거나 Flush되면 버스 프로토콜이 깨짐 |
| **3순위** | **동기 예외 순차 플러시 (`TrapFlush`)**<br>*(`ID/EX` 또는 `EX/MEM`에 예외 존재)* | `PC Stall` + 예외 뒤쪽 단계 Flush (`4'b1100` 또는 `4'b1110`) | WB 도달까지 **2~3사이클** | 예외 명령어 뒤의 젊은 명령어가 EX에서 분기하거나 Stall을 거는 것을 즉시 무효화해야 함 |
| **4순위** | **EX 단계 일반 분기 (`TakeBranch`)**<br>*(Taken Branch / `JAL` / `JALR`)* | `PC <= BranchTarget`, `IF/ID` 및 `ID/EX Flush` | **2사이클 버블** (ADR-002) | EX 명령어의 분기가 확정되었으므로 잘못된 경로인 ID 단계 명령어의 Load-use/CSR 정지를 무시해야 함 |
| **5순위** | **Load-use / CSR-use 정지**<br>*(`WB_MEM` 또는 `WB_CSR` 의존성)* | `PC Stall` + `IF/ID Stall` + `ID/EX Flush` (버블 1개) | **1사이클 버블** (ADR-004) | EX/MEM으로 진행하는 생산자 명령어를 기다리기 위해 ID 단계 소비 명령어를 보존해야 함 |
| **6순위** | **CSR 직렬화 정지 / 인터럽트 드레인**<br>*(`CsrStall` 또는 `TrapDrain`)* | `PC Stall` + `IF/ID Flush` (앞선 명령어들은 계속 진행) | CSR **3사이클** / Drain **0~4사이클** | 파이프라인 내부 명령어들의 정상 진행(배출)을 막지 않으면서 새로운 명령어 유입만 차단함 |

### 4. 결정 및 근거

- **선택:**
  1. **동기 예외(WB Commit + 순차 Flush, 고정 3사이클 전파)와 비동기 인터럽트(Pipeline Drain 후 진입, 가변 0~4사이클 대기)의 이원화 타이밍**을 채택한다.
  2. 다중 제어 충돌 시 **`트랩 분기 확정(1순위) > 버스 대기(2순위) > 동기 예외 순차 플러시(3순위) > 일반 분기(4순위) > Load/CSR-use 정지(5순위) > CSR 직렬화 및 인터럽트 드레인(6순위)`**의 6단계 우선순위를 적용한다.
- **근거:**
  1. 동기 예외를 비동기 인터럽트보다 앞선 우선순위로 두면, 예외 명령어가 WB에서 트랩으로 진입함과 동시에 하드웨어가 `mstatus.MIE <= 0`으로 인터럽트를 마스킹하므로 두 트랩이 같은 사이클에 충돌하지 않고 순차적으로 안전하게 처리된다.
  2. 버스 대기(`BusStall`, 2순위)를 일반 분기나 예외 전파보다 위에 두어 진행 중인 버스 트랜잭션을 보호하고, 트랩 분기 확정(`TrapBranch`, 1순위)은 모든 선행 명령어(MEM 단계 포함)가 완료되거나 취소된 시점에만 발생하므로 최상위에 두어도 버스 충돌이 일어나지 않는다.
- **감수 사항:** 최악의 경우(예: 파이프라인 포화 상태에서 APB 주변장치 접근(2사이클 대기) 중 외부 인터럽트 발생) 드레인 완료까지 `4사이클(기본 드레인) + 2사이클(APB 대기) = 6사이클`이 소요될 수 있다.

### 5. 결과 및 검증

- **복합 시나리오 검증:**
  1. `ECALL`이 ID/EX에 있을 때 외부 인터럽트(`MEIP`) 동시 인가 → `ECALL`이 먼저 WB에서 트랩 진입(`mcause = 11`)하고 핸들러에서 `MIE`를 다시 켜거나 복귀한 뒤 인터럽트가 처리되는지 확인
  2. taken 분기 명령어(EX) 바로 뒤에 불법 명령어(ID)가 들어온 경우 → 4순위 일반 분기(`TakeBranch`)가 ID/EX를 Flush하여 잘못된 경로의 불법 명령어가 예외를 일으키지 않는지 확인
  3. APB 주변장치 Load/Store 실행 중 인터럽트 인가 → 2순위 `BusStall`로 버스 응답을 끝까지 마친 뒤 6순위 `TrapDrain`으로 안전하게 배출되는지 확인
